
一、 核心架构与代码设计原则（Architecture & Design）

1. 模块化划分：按工程模块进行严格目录划分，每个模块一个独立目录。
2. 职责单一化（KISS原则）：按功能进行类型（Class / Module）划分，每个类型只处理固定的单一职责，严格遵循 KISS（Keep It Simple, Stupid）原则。
3. 单一操作原则：类型中的每个方法只做一件事。
4. 集中流程调度：必须使用专门的流程调度类/编排器（Orchestrator）对各类型进行统一流程调度，严禁在各模块中进行随意、散落的互相调用。
5. 见名知意（禁止简写）：模块名、类型名、方法名、变量名必须做到见名知意，严禁使用任何缩写、简写或无意义单字母（如 tmp, data1, mgr 等）。

二、 核心工作原则（Golden Rules）

1. 先读后写：在修改任何文件之前，必须先使用工具读取该文件及相关依赖，严禁凭空盲猜代码结构。
2. 最小修改原则：只修改与当前任务直接相关的代码。不要擅自重构无关模块、不清理未要求清理的注释、不升级无关依赖库。
3. 保持原子性：一个 Agent 会话只解决一个明确的小任务（Issue / Bug / Feature）。如果任务过大，必须先输出拆解计划，征得人类同意后再分步执行。
4. 禁止静默失败：如果遇到不确定的类型定义、API 变动或逻辑冲突，立即停止并向人类提问，严禁擅自做假设去“猜”一个实现。

四、 常用构建与测试命令（Commands）

在提交任何代码前，AI 必须在沙箱或本地运行以下命令，确保无报错：
• 安装依赖：[例如：poetry install]
• 运行单测：[例如：poetry run pytest tests/]
• 代码检查（Linter）：[例如：poetry run ruff check .]
• 启动服务：[例如：poetry run python main.py]
⚠️ 铁律：如果测试未通过，严禁直接向人类宣称“任务已完成”，必须自主定位错误并修复，直到测试绿灯。

五、 代码风格与规范（Code Style）

• 类型注解：所有函数必须带有明确的参数及返回值类型注解（如 Python 的 typing）。
• 日志输出：关键业务逻辑必须包含结构化日志（Logging），严禁使用 print() 作为生产环境输出。
• 错误处理：捕获异常时必须明确具体异常类型，禁止使用空的 except: 吞掉错误。
• 注释语言：代码内注释一律使用中文，简明扼要说明“为什么这么做”，而不是复述代码字面在写什么。

六、 安全与权限红线（Safety & Boundaries）

• 高危操作确认清单：以下操作在执行前必须向人类请求显式批准：
	• 执行带有删除性质的 Shell 命令（如 rm -rf、DROP TABLE 等）；若需删除文件，一律移动到 .trash 目录中，严禁直接物理删除。
	• 修改或读取环境变量及敏感配置文件（如 .env、secrets.json）。
	• 引入或更新第三方依赖包（如修改 requirements.txt / pyproject.toml）。
• 敏感信息保护：严禁将任何 API Key、密码、Token、私钥硬编码（Hardcode）到代码或日志中。

七、 输出与交付规范（Output Format）

每次任务结束时，AI 的最后一条回复必须按以下结构输出：
1. 修改清单：列出本次动了哪些文件，主要改了什么。
2. 验证结果：附带你运行过的测试命令及终端输出结果。
3. 遗留问题/建议：如果有未尽事宜或潜在风险，明确告知人类。
